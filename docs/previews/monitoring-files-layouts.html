Monitoring · Browsing a device's files

Jose, 2026-10-01: “me who has access to monitoring being able to access files on one of my employee’s computers… ask ui-ux for a good layout for it too.”

Pick one desktop layout (1–3) and one phone layout (4–6), for example “1, 4”. Nothing is built yet — Monitoring is scoping the agent side. These are the screen only.

What exists today in Monitoring: General (the ownership chart), Map, PC Specs (the machine roster), Camera Monitoring, and Desktop Monitoring (live view + remote control). Every pane is person-first, polled, and honest about staleness — a frame or a reading is never shown as more current than it is. Files slots in next to them in the same language.

Every option keeps four things, because this is a privileged act, not a casual one:

  • Gated per device by reach and the current view, the same as the rest of Monitoring — the Files tab is only drawn, and the server only answers, for a device you can reach from where you are standing. A new grant, monitoring.files.view (download is its own, monitoring.files.download).
  • Accountable, visibly. The person’s name sits on the device, and ◎ Opened by you · recorded rides next to the path — every open and every download writes to the audit trail (monitoring.files.opened / .downloaded), exactly as taking control does.
  • Honest about the poll. It is not a local file picker: pick a device → ask for a folder → the agent answers on its next beat (~1–3 s). Every navigation has a brief fetching… beat, shown as the last listing dimmed with the path being asked for and how long it has taken — never a frozen screen pretending to be instant.
  • Downloads are two steps. A file is Requested, the agent uploads it on a later beat, then it is Ready · Save. No click ever blocks on a transfer.

1Its own Files tab — a person rail, a breadcrumb, one list Recommended

Mirrors Desktop Monitoring exactly: pick a person on the left (their device and whether it is on), and the right pane is a breadcrumb over a single list — folders first, then files with their size and when they changed. Folders open in place; files download. The accountability chip sits on the path, where you cannot miss it. Recommended because it reuses the module’s own person-first rail and one honest, scannable list, so Files reads as part of Monitoring rather than a bolted-on explorer.

server A poll-driven directory read: the viewer POSTs list for a device + path, the agent answers on its next beat with entries {name, is_dir, size_bytes, modified_at}; a new native files capability on the agent and a cache queue like Remote Control’s input. Start points (drives, the user’s folders) come back from a roots call. Download = request a path → agent uploads to a short-lived store (like screenshots) → a signed “ready” URL. Offline and last-seen are the device row you already have.

2Its own Files tab — a folder tree beside the list

For deep digging. The left is a folder tree you expand node by node; the right shows the chosen folder’s files. The breadcrumb still runs across the top, and the accountability chip still rides the path. More powerful for a known deep path — and more poll beats, because every node you expand is its own request, so a branch opening shows a small spinner on that node.

server The same list call as option 1, once per expanded node rather than once per visited folder — so the tree does more round trips. A node that comes back refused draws a small lock rather than children. Everything else (roots, download two-step, offline) is identical.

Recommendation

Desktop 1 and phone 4. Option 1 reuses Desktop Monitoring’s own person rail and keeps the whole act in one honest list, so Files reads as part of Monitoring rather than a borrowed file explorer; the breadcrumb carries the recorded chip where no one can miss it, and the dimmed-last-listing beat is the same honesty the capture tab already keeps. Option 4 is that same list one-job-per-screen, where the drill-in is the poll — every tap already expects a beat — with the recorded chip pinned above every folder. Option 2’s tree is worth keeping in reserve for a future “go straight to a deep path”, but it multiplies poll beats and is the wrong default. Option 3 (launched from PC Specs) is genuinely useful and could ship as well — the Browse-files action on a card costs little and answers “while I’m looking at this machine, show me its files” — but as the only way in it buries the feature inside another tab.

What the server still owes, shortest list: a native files capability on the Windows agent; a poll-driven list (device + path → entries) and roots (drives + the user’s folders), on the same cache-queue shape as Remote Control’s input; a two-step download (request → short-lived upload store → signed “ready” URL, like screenshots); monitoring.files.view and monitoring.files.download grants, §3-scoped by reach and current view; audit events monitoring.files.opened / .downloaded; and per-folder error slugs from the agent (denied / not-found / offline), worded on the client exactly as the capture tab words its last_error. Option 6 additionally needs a find (search) request.

People, machines, paths, files, sizes and times are invented. The real screen reads only devices you can reach from the current view, in the organization’s time zone, and records every open and download.
