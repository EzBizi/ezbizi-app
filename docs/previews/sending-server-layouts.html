A mail server for sending — pick one desktop and one mobile

The screen state B has been pointing at with no destination. Shape from SES after the fork landed with Email: a business connects its own server for sending — host, port, username, password, encryption — stored on the sending identity and scoped organization / company / franchise. The convenience is an explicit “use the same server as info@” that copies the values and says so. Never an implicit fallback, because with one nobody can tell by looking which credential is actually in use.

⚠ THE COPY FLOW IS PARKED, AND THREE OF THE STATES BELOW GO WITH IT. Corrected 2026-09-15, after SES read this drawing properly. copied, inherited-and-copied and copied-then-that-mailbox-changed are not being built, for three reasons that stack:

1 — the facts are not stored. The copy line needs which mailbox, when, and by whom. SendingIdentity::connectServer writes host, port, username, password and encryption, and nothing else — verified in the source, not remembered. Drawing the line would mean inventing a source, a date and an actor.

2 — the stale-copy line is not a missing column, it is a missing relationship. “The password on info@ was changed on 2 October; this server still uses the one copied in September” requires comparing this credential against the mailbox it came from. With no source recorded there is no mailbox to compare against, so it cannot be derived at all.

3 — and this is the one that decides it: there is nothing to copy FROM. SES relays a deploy-desk measurement of production — 6 mailboxes, 0 with a mail server, 0 with credentials, all gmail_workspace, which carries no SMTP host. So “use the same server as one of your inboxes” would open onto an empty list for every business that exists. (Relayed through two sessions and not measured by me. The storage claim in 1 I did check.)

Consequence for this drawing, and it is mine rather than theirs: the second fact row now renders only when there is a source to name, instead of always. It used to fall back to “Typed here”, and with copying parked that is the only thing it could ever say — a row of constant text reads as information and carries none. Worse, nothing records that a value was typed, so the sentence would be an assumption rendered as a fact: the exact thing a derived sentence is supposed to replace. Switch the state picker to a copied state to see the row appear. That is what it will look like when the copy flow arrives and brings its own storage.

The whole design problem is that there are TWO facts here and they are independent. Whose value is this — the cascade’s question, which this screen already has words for: Set here, Inherited from {name}, EzBizi default, and its own docblock warns “the third is not a rounding of the second”. And where did these values come from — typed, or copied from a mailbox. A franchise can inherit a value that was copied, so one status line cannot carry both without merging them, which is the defect the last three entries have all been about. The three options differ in how they keep the two apart.

The state worth switching to first is “copied, then that mailbox changed”. A copy does not follow its source — that is the point of copying rather than linking — so the screen has to be honest about it rather than implying a live connection.

⚠ AND THAT STATE IS DRAWN AGAINST A SIGNAL THAT DOES NOT EXIST YET. Read this before treating it as covered. SES raised it and they are right: a copied password that no longer authenticates is not a display problem with a display fix. The send does not degrade, it FAILS — on a schedule, to somebody expecting a report. So the sentence on this screen is necessary and nowhere near sufficient: something has to NOTICE, and nothing does today. The state is drawn so the screen is honest once there is something to be honest about; it is not evidence that anybody will ever be told. Detection is SES’s, and where a noticed failure SURFACES is a drawing I will make when there is a signal to draw against — the same way entry 12’s states waited for what the server could prove rather than being invented first.

UPDATE: there is now a signal, and the four failure states below are SES’s measurement rather than my invention. I asked what the server can PROVE before drawing anything, and the answer had a condition that settled their transport choice: on Mail::build you get one exception with the SMTP code buried in its message — classifying that is parsing an error string, which is the thing I drew once this week and will not draw again. On the Email module’s own socket the numeric reply codes are read and already sorted. So they are building on that one.

Four, not three, and the split that matters is 4xx against 5xx. A 5xx will not change and sends somebody to the account; a 4xx is “not now” and must not — a temporary refusal that tells you to check your password is the confident wrong cause this whole queue keeps circling. And “never tried” is a timestamp with no inference in it, which is the state every row is in the moment it is saved.

What is still NOT drawn: where a failing scheduled report gets NOTICED. This screen is where somebody already looking will find out. Nobody checks it. That surface is a separate drawing and I am not stacking it on top of an unpicked one.
