Optimising for: the return visit. The screen is a list of your suggestions split by whether EzBizi has answered yet; writing a new one is one button among them.

Read from the built backend (f13dd81..f845c4e), not assumed GET /api/v1/suggestions returns {id, body, status, decision_note, decided_at, created_at}, newest first by created_at and by nothing else. This layout's two groups — Waiting on EzBizi and Answered — are the client's own arrangement over that one order, which is worth saying out loud because it is the only thing here the server does not do for you. There is no reviewer name and no thread. decided_by exists in the table and is not in this payload, and there is exactly one note per suggestion. The answer is EzBizi's, unsigned, and it cannot be replied to. 2000 characters; an empty body is refused with "Write the suggestion first." Nobody at your own organization can read these, which is why the module writes no audit row at all — an audit line naming the sender would publish the one thing this table keeps private.
The one rule that has to be visible rather than described Edit and Withdraw exist on a new one and on nothing else. An author may correct or take back a suggestion only while nobody has read it, and the server enforces it on both endpoints. In this layout the pair lives in the detail footer, so the test is easy to run by eye: select the New one and the footer has two buttons; select any other and the same footer carries the server's sentence instead —
  • In review — "Somebody at EzBizi is reading this one, so it is fixed while they do."
  • Approved / Denied — "This one has been answered, so it stays as it was written."
The grouping costs something here and it should be said. Putting New and In review together under Waiting on EzBizi is honest about the author's question — neither has been answered — but it puts the editable one and the frozen one in the same bucket. The rail row for a New one therefore carries its own line saying it can still be changed, so the difference does not depend on selecting it.
Two answers, not one Pick a desktop number and a phone number, and they need not match. There is no split pane at 375px, so this layout's phone answer is the same idea in the native form: a segmented Waiting / Answered filter over one list, each row opening a screen. That is a real design rather than this one narrowed, and it can be chosen on its own.
2 · What happened to what you sent A 320px rail of your suggestions grouped by whether they have been answered, and a reading pane beside it. The rail is 320 rather than the app's usual 200 because a suggestion has no name — its own first line is the only thing that identifies it, and below about that width every row starts "Could we..." and looks the same. What it trades away: composing is demoted to a button, so the tab is worse at the thing it exists for and better at the thing people will actually do more often. It is also the most machinery for the common case of owning two suggestions, where a rail of two rows beside a mostly empty pane looks like a screen waiting for content.

Desktop — a denied one open, so the reviewer's words are in full

The footer is the thing to look at. Here it carries the server's own sentence and no buttons. The answer is a block in the reading pane rather than a caption, at full width and full size, because a decision note is somebody's considered reply and setting it in 12px grey would say the opposite.

Desktop — the New one open, which is the only one you can still change

Same footer, two buttons. Edit turns the reading pane into the compose box in place; Withdraw is a second press in the footer rather than a dialog — constraint 1, no modals, including confirm-before-destructive. Note the rail row also says "you can still change this", so the difference is visible without selecting anything.

Desktop — the one being read, which is frozen but not answered

The third state, and the one a layout is most likely to forget because it looks like nothing has happened. The footer carries the server's other sentence — somebody is reading it, so it is fixed while they do — and there is no answer block, because there is no answer. The rail row for it sits under Waiting on EzBizi beside the New one and carries no "you can still change this" line, which is the whole difference between the two rows in that group.

Desktop — the first visit

With nothing in the rail there is nothing to select, so the pane says what the tab is for and opens the box. The rail keeps its Write button so the layout does not rearrange itself the moment the first one lands.

375px — designed for the phone, not narrowed

A split pane does not exist at 375px, so the split becomes a filter. Waiting and Answered are the two questions somebody opens this on a phone to ask, and each row opens one screen. The detail screen keeps the footer, which is where the presence and absence of Edit and Withdraw stays visible on a phone.
