Optimising for: getting to the bottom of the queue. One table in the server's order, one line of each suggestion, and the row opens where it sits to be answered.

Read from the built backend (2f01245, f845c4e), not assumed GET /api/v1/staff/suggestions returns {id, organization, organization_id, author, body, status, decision_note, decided_at, created_at}. The order is the server's and a design must not re-sort it: undecided first, then being read, then everything decided — and inside each band, newest created_at first. So the decided band is ordered by when a thing was sent, not when it was answered: today's answer does not come to the top of it. 200 rows, no paging, no search parameter. limit(200) with nothing after it, so a design must not promise a total, a page 2, or a server-side filter. Filtering is the client's, over what has already arrived. decide takes reviewing, approved or denied. Never new — you cannot put one back and hand the author the right to rewrite text you have read. A second decide on a decided one is accepted and replaces both the status and the note, so the control has to stay reachable on a decided row. Approving or denying writes the author a notification. Marking it in review does not, deliberately — nothing has been decided yet. Two fallbacks that will appear in production: the author reads "Somebody who has since left" when the user row is gone, and the organization reads "Unknown". Both are long, and both are drawn below rather than assumed away.
Three things about the decide control that came out of the code, not the drawing Denying with no note is refused, and the sentence is the server's: "Say why, in a sentence. The person who sent it reads it." It is a 422 on the note field, so it is reported at the field and retried with the same button — a refused save, never a reload. Approving with no note is legal, and it should not be. The notification's body is the note, so an approval with an empty note sends somebody a bell that says "Your suggestion was approved" and nothing else. The server permits it; the screen should press for a sentence anyway, which is why Approve here carries the same field and the same prompt as Deny. Marking one "In review" must not offer the note field. decide writes whatever note it is given into decision_note, and the author's own payload carries decision_note whatever the status is — so a note typed beside "In review" appears on the author's screen with no notification and no explanation. All three layouts therefore make "Mark in review" a bare button.
One thing worth your ruling, and it is not about this screen alone This is the seventh chip in the Development tab strip. TabBarLike puts its chips in a horizontally scrolling row, and the house rule is that chrome wraps rather than scrolls — a tab strip has no natural width, so making somebody drag it sideways is spending a gesture on a list of labels. It is a SingleChildScrollView(Axis.horizontal), so it scrolls by construction rather than only when it happens to be too wide, and the six labels already there do not come near fitting 375px. A seventh makes it worse rather than causing it. The fix is one line and it is not this module's file — TabBarLike is shared with Automations, so changing it changes two screens. Layout 1's drawing shows the strip wrapped, which is what it would look like fixed. Say the word and it goes in with the build; otherwise the seventh chip lands in a strip that scrolls.
1 · A worklist you go down One table, the server's three bands as headings, one line of each suggestion beside its organization and author, and a row that opens in place to be read and answered. It is the densest of the three — nine rows fit above the fold where the other two show one or four — and it is the only one where the shape of the whole queue is a glance: how many are waiting, how many customers they came from, whether one organization is sending everything. What it trades away: a suggestion is free text and a table row is one line of it, so triage happens on a truncated sentence and the useful half is often the second one. Opening a row also pushes everything below it down the page, so working the queue means the rows keep moving.

Desktop — the queue, with one row open to be answered

The bands are the server's order made visible — Waiting, Being read, Answered — not a client-side sort. Every row carries the organization and the author because this list spans every customer and "who is asking" changes what the answer should be. The decided rows keep a Change-the-answer button, because decide accepts a second decision and a reversal is a real event.

Desktop — Deny pressed with an empty note, and refused

The server's own sentence, at the field it belongs to, with the field outlined in the error colour and the button unchanged so the retry is the same press. No reload anywhere near it: this is a refused save, and offering to retry it by reloading would offer to recover the note by discarding it.

375px — designed for the phone, not narrowed

A nine-column table cannot narrow, so on the phone it stops being a table. Each row becomes a card carrying the three things triage needs — state, who, and the first two lines — and answering is its own screen with the actions docked above the keyboard, because a note is typed and Approve must not be behind the keyboard while you type it.
