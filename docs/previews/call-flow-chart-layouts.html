The picture is not what earns this screen. The two states are. Phone built the data and named them, and they are the whole argument: dead — a caller can reach it and nothing useful happens, an option pointing at a number nobody set, a ring group with nobody in it. skipped — a step the caller passes straight through that plays nothing. Corrected 2026-09-15: this said “never reached at all” until Phone measured their own renderer and found the node is linked into the chain (arrival → menu → answer) — it is ON the flow, not beside it. Callers sail past and hear nothing, nobody complains because the caller does not know they missed a menu and the owner does not know theirs is silent. A flowchart that draws a dead branch identically to a live one is prettier than the list and less useful, so every option below is judged on whether you can see those two without reading node by node — which is why each carries a count at the top.

⚠ REDRAWN 2026-09-15 against the THIRTEEN REAL LINES rather than fixtures. Phone read production instead of trusting their own test data, and two things in it change what these optimise for. Not one line has an opening-hours schedule. It is supported and it renders, but a layout leaning on hours as the early branch that sets the rhythm has an empty column on every line Jose will actually open — the first branch he sees is the menu, so that is what is drawn. And the cycle is the common case, not the edge case: eleven of thirteen lines have overflow = queue, so the queue ⇆ ring group back-edge is what the tab looks like normally. Judge the options with it rather than without. The typical line is caller → arrives → menu (4 keys + no key) → ring group → queue ⇆ ring group → voicemail; the other two lines are four nodes, one of them dead. Switch between them below — a chart that looks broken at four nodes is reporting the truth, and one that only reads well at eleven is tuned for a line that does not exist.

Facts the layout may rely on, measured rather than assumed (TwimlRenderer::graph(), and a test that sabotage-checks): exactly one entry node, always caller; every node reachable from it and no edge dangling, so no defensive drawing for orphans; and it CAN cycle — queue → answer → queue and a “play the menu again” key are real, so a naive walk loops and a layered layout needs a back-edge that is drawn rather than followed. Six nodes without a menu, about eleven with a four-option one: small enough that nothing here needs virtualising. One graph per line, and a company can have thirteen, so every option carries the line picker the existing pane already uses.
