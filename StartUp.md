# StartUp

Read this before touching anything. It is the front door for a developer or a coding
agent joining EzBizi, and it exists because most of what follows is not written down
anywhere else — it is a working agreement, arrived at over weeks, mostly the hard way.

It deliberately contains **no numbers that change**: no test counts, no version, no
row counts. Those live in `docs/EZBIZI-STATUS.md`, which is regenerated by the
deploy. A second copy of a moving number is a lie with a timestamp on it.

---

## 1 · What this is

EzBizi is a multi-tenant SaaS field-service CRM. It is a **clean rewrite** of an
older product, A1 Tools, which is still live and still serving a real business.

| | |
|---|---|
| Backend | Laravel 13 · PHP 8.4 · MySQL 8 — repo root |
| Client | Flutter **web** — `client/` |
| Customer app | https://app.ezbizi.com |
| Control plane | https://dev.ezbizi.com |
| Server | one AWS instance, SSH alias `app` |

**A1 Tools may be read for reference. Its code must never be copied in.** Its
problems came from its structure, so importing a working function imports the reason
it has to be rewritten. Read it to learn what the business needs, then build that
against this architecture.

## 4 · The three rules that protect production

These are the ones that have actually caused damage. In order of how expensive it is
to get them wrong.

### Never edit on the server

Edit locally. Ship with `scripts/deploy.sh`. Server-side edits are for **diagnosis
only** — reading a log, checking a permission, confirming what is actually deployed.
An edit that lives only on the box is erased by the next release and will not be
missed until it is needed.

### Never point a sandbox at production

`.env` **and** the cached config both resolve to live data, and both have to be
overridden. `scripts/sandbox.sh <name>` exists to do that correctly:

```bash
scripts/sandbox.sh mywork          # create
scripts/sandbox.sh mywork --sync   # push local changes into it
scripts/sandbox.sh mywork --verify # confirm it is not looking at live
scripts/sandbox.sh mywork --rm     # tear down
```

Use it. `--env=testing` alone has silently fallen back to production before, and the
sandbox directory lives at `/opt/ezbizi-test` rather than beside the production
`.env` for exactly that reason.

### Never let a workflow and a hand edit touch the same file

If a background agent or a parallel task owns a file, do not also edit it. A
full-file write silently destroys the other's work with no conflict and no warning.
Wait, or take the file over explicitly.

### Committing on a tree many sessions share

"Stage by path, never `git add -A`" is not enough, and saying it was cost a day.
One file was fixed and silently reverted three times in an afternoon — the third
time twelve minutes after its session had been warned. `git log` showed every
restore sitting in history looking fine while the content was gone.

**There is one rule, and every tool is unsafe without it and safe with it:**

> **Resolve the base at commit time and parent onto that same commit.** Not at
> review time, not at build time. If more than a few seconds pass between reading
> a blob and `commit-tree -p <base>`, rebuild the blob.

Partial commit, `hash-object`/`update-index`, and the private index are all
equally unsafe if the base drifts, and all equally safe if it does not. Reach for
whichever suits the file; the rule is the same.

**Why the tool is not the fix.** One revert today used a private index correctly:
`read-tree HEAD` took the *current* tree, then `--cacheinfo` overwrote two paths
with blobs computed from a HEAD twenty minutes older. Everything committed in
between reverted, silently. The guard its author was proudest of — asserting
another session's uncommitted hunk was absent from their blob — was correct when
built and became the instrument of the revert once that hunk was committed. The
private index stops you disturbing the shared index, which is real and worth
having. **It does nothing about a stale blob, and a stale blob is what bites.**

One commit can revert through two surfaces at once. `358b3db` removed three phone
routes through its `routes/api.php` blob *and* deleted eight files through its
stale tree — 2,004 deletions across three unrelated modules, no conflict.

```bash
BASE=$(git rev-parse HEAD)                 # resolve ONCE, here, immediately
export GIT_INDEX_FILE=$(mktemp -u)
git read-tree "$BASE"                      # replaces this index; ignores .git/index
git add <your paths>                       # or update-index --cacheinfo for a blob you built
TREE=$(git write-tree)
git diff-tree -p "$BASE" "$TREE" -- <your paths>    # ← READ THE HUNKS. Not the stat.
COMMIT=$(git commit-tree "$TREE" -p "$BASE" -F msg)
git update-ref refs/heads/main "$COMMIT" "$BASE"     # fails if main moved

unset GIT_INDEX_FILE
git reset -q HEAD -- <your paths>          # ← STEP 8. Not optional. See below.
scripts/index-landmines.sh                 # must read 0 stale, 0 live
```

**THE INDEX RE-ACCUMULATES, SO CHECK IT IMMEDIATELY BEFORE EACH COMMIT — NOT
AFTER THE LAST ONE.**

A session disarmed six stale paths straight after committing and `index-landmines.sh`
read `0 stale, 0 live`. **Minutes later the same six were staged again** — almost
certainly another session's `git add -A` sweeping the whole tree. A second session
hit it independently within the hour.

So disarming after a commit is a courtesy to whoever commits next; it protects
nothing of yours. **The index you cleaned ten minutes ago is not the index you are
about to commit from**, because it is shared and anybody's `git add -A` refills it
while you are typing.

That makes the pre-commit check the only thing that actually works, and its result
expires the moment you look away:

```bash
./scripts/index-landmines.sh     # immediately before EVERY commit, every time
```

It is also the same shape as the rest of this file one level down: every
measurement here has turned out to be a claim about a MOMENT rather than a state
— a worktree count, a golden image, a baseline taken before a merge. A clean
index is one more of those, and it is the one that eats work rather than merely
misleading somebody.

**And clear other people's stale entries without asking.** From outside you cannot
tell whether somebody is mid-edit, but the failure mode of clearing is one
`git add` and the failure mode of waiting is somebody else's commit eating the
work. Clearing is cheap and reversible; waiting is neither. `git reset` writes the
index and never the working tree.

**BEFORE ANY OF THAT: `git commit -- <paths>` is the safe everyday form, and it
is one word different from the dangerous one.**

```bash
git add -- StartUp.md && git commit -m "..."     # ← commits the WHOLE INDEX
git commit -m "..." -- StartUp.md                 # ← commits ONLY that path
```

`git add` stages one file. `git commit` then commits **everything staged**,
including whatever fifteen other sessions left in the shared index. The pathspec
form builds the commit from HEAD plus those paths only and ignores the rest of
the index entirely.

Proven, not assumed: with a staged deletion of `victim.txt` sitting in the index,
`git commit -- keep.txt` produced a one-file commit and `victim.txt` survived in
HEAD.

**This is not hypothetical and it is not rare.** On 2026-08-31 a commit intended
to add 25 lines to this file committed **16 files and 1190 deletions**, destroying
two finished Phone features — two controllers, two models, both migrations, both
test suites, and 122 lines of routing — because the shared index held stale
deletion entries. It was written by the session that spends its day telling
everyone else to run `index-landmines.sh` first, and that session did not run it.
That is the point: a rule you have to remember fails exactly when you are busy,
and the person most familiar with it is not exempt.

The pathspec form removes the failure mode instead of asking you to notice it.

It does **not** disarm landmines that are already there — those stale entries stay
staged for whoever commits next without a pathspec. Clearing them is still
`index-landmines.sh` plus `git reset -q HEAD -- <paths>`. But you can no longer
fire somebody else's.

**When you REPAIR one of these, rebuild a contended file as CURRENT HEAD plus
your own lines — never as your old copy of it.**

The obvious instinct is to restore your version of `routes/api.php` wholesale.
That rolls back everyone who touched it since, which is a revert committed while
repairing a revert, and it is the third one nobody notices. Restore deleted files
from the ORIGINAL COMMIT'S BLOBS so what lands is byte-identical to what was
tested, and rebuild shared files by re-applying only your own block on top of
whatever HEAD says now. Then verify the other blocks survived: after one repair
the check was web/sites 5 routes, inspections/codes 5, phone/trust 4,
phone/ports 2, all intact alongside the restored ones.

The trap is not obvious until you are standing in it, and you are standing in it
while relieved that you spotted the first problem.

**And check what you actually committed, every time:**

```bash
git show --stat HEAD
```

A stale blob does not change WHICH files appear in your commit — it changes how
many lines. The commit above would have read *16 files, 1190 deletions* to an
author who meant to change a word count. One line of output, read once, catches
every instance of this.

**AND IT ARMS EVERYBODY ELSE'S EARLIER RESETS, WHICH IS THE HALF THAT GETS
MISSED.** Reproduced in a scratch repo on 2026-09-01:

    session A:  commits by pathspec, then `git reset -q HEAD -- p.txt`
                -> shared index clean, 0 staged
    session B:  commits p.txt via a PRIVATE index + update-ref
                -> shared index now shows 1 staged file, reverting B's change

A pathspec commit UPDATES the shared index for its paths, so a prior reset stays
harmless. A private-index commit deliberately does not touch the shared index at
all — so HEAD advances while A's reset blob sits there, and that blob is now a
staged revert of B's work.

**Neither session did anything wrong on its own.** A followed the rule; B used the
safest commit method in this file. It takes both, which is why one session hunting
a "phantom index saboteur" found only their own resets and concluded it was
self-inflicted — it was not, and there was no saboteur either.

So step 8 is load-bearing in both directions: it disarms the revert your own
commit created, AND it clears the older resets your commit just turned into
reverts. A private-index commit that skips it leaves a landmine armed by somebody
who was being careful.

**Step 8 is not tidying — it disarms a revert your own commit just created.**
The private index leaves the SHARED `.git/index` untouched, which is the whole
point of it. So that index still holds every one of your paths at its
*pre-commit* blob, and the instant `update-ref` moves HEAD those untouched
entries become an armed revert **of the commit you just made**. The next bare
`git commit` by any session re-applies them, under a message about something
else.

It does not take two sessions and it is not bad luck. Observed on a five-line,
comment-only commit: `index-landmines.sh` read `0 stale, 0 live` before, and
`+0 -5` against that very file after, with nobody having staged anything.
Every careful private-index commit leaves one behind for every path it touches.

`git reset` writes the index and never the working tree. Its "Unstaged changes
after reset:" output lists every path where worktree and index differ repo-wide,
not what it touched — ignore it and let the landmines script confirm instead.

**Read hunks, not a stat, and read them against the tree you are about to commit.**
Every other check here counts files; only this one shows you *whose lines* they
are. `git add <path>` stages the **working tree** version of that path — so the
private index answers "which files am I committing", and answers nothing at all
about "whose version of this file". Another session editing the same file on disk
has its work taken by your `git add`, silently.

That has already happened to somebody running the full recipe correctly: they
verified 1 file, 15 insertions, 6 deletions, and the commit landed as 49 — a
thirty-line guard from another session, carried in under a message about something
else. They only noticed because they compared the numbers afterwards and were
suspicious of their own commit.

`$BASE` appears four times and must be the same SHA every time. Resolving `HEAD`
twice is how the drift gets in, and it looks careful while doing it.

**The checks need a pinned base too, not just the commit.** `git diff --cached`
resolves `HEAD` at the instant it runs, so on a tree many sessions commit to it
diffs a moving ref and reports the answer as a fact about a fixed thing. Two
readings minutes apart were both correct and disagreed, because a commit landed
in the gap. Use the pinned forms:

```bash
git diff-index --cached --stat "$BASE"
git diff-index --cached --diff-filter=D --name-only "$BASE"   # staged deletions
```

The second one is the only thing that reveals a staged deletion. `git status`
prints the reassuring `??` for a file that exists on disk directly beneath the
staged `D` for that same path, one line apart.

**If you are an agent, each tool call is a fresh shell and `$BASE` does not
survive between them.** Write it to a file and read it back; never re-resolve
`HEAD` in the later call. One revert happened exactly here — `read-tree HEAD` in
one call, `commit-tree -p $(git rev-parse HEAD)` in a later one. The compare-and-
swap passed because the *pointer* was current; the *tree* was twenty minutes old.
17 files and 202 deletions where 15 and 29 were intended.

**The stat check catches a stale base. It cannot catch a stale blob** — the file
list is right while the contents are old, which is exactly how one revert got
through with its author watching: 24 intended paths, nothing foreign, and two of
them carrying twenty-minute-old content that reverted another module's routes. If
you splice blobs in by hand, diff each spliced path against `$BASE`'s version of
that path, not just the file list.

**And it is blind to a rename**, which shows as `0` changed lines and moves no
count you would glance at. One commit whose message said "docs" carried half of
another session's `git mv` out of the shared index — a class renamed in its path
but not in its declaration, so PSR-4 could not autoload it. Read the *paths* in
the stat, not only the numbers: a `{old => new}` arrow you did not intend is the
whole signal, and there is no line count to catch it.

Clearing a stale entry is safe when you can show it is stale: `git reset HEAD --
<path>` writes the index only and never touches the working tree, so after it,
`git show HEAD:<path>` and the file on disk should still agree. Do that only for
paths you own, and only after proving the staged copy is older than `HEAD` —
otherwise you are discarding somebody's in-flight work to prevent a commit nobody
has made.

**There is a form that is safe even on somebody else's paths:** show the staged
blob is a **strict subset** of `HEAD` — zero added lines. Then clearing it can only
remove a landmine and cannot lose work, and you do not have to wait for an owner
who may not exist any more.

**But "adds lines" does not mean "is new work".** A stale copy of a file whose
lines you *changed* appears to add content — its additions are the old versions of
the lines you replaced. That test raised a false alarm on this very file within an
hour of being written. When the staged copy adds something, check whether that
content exists in an **earlier commit** of the same path before concluding somebody
is mid-edit:

```bash
git show <earlier-sha>:<path> | grep -F "<the added line>"
```

A hit means stale. Only genuinely novel content — present nowhere in the file's
history — is somebody's in-flight work. Leave that, and tell them. Line counts are usually enough to show staleness; a marker string the
newer version contains and the older does not is better, because it names the
regression instead of implying one.

**Ignore what `git reset` prints.** "Unstaged changes after reset:" lists every
path where the working tree differs from the index **repo-wide**, not what the
command touched — so it will name other sessions' files and read exactly like you
have just clobbered their staging. A path-limited reset cannot touch anything
outside its pathspec. Do not try to "fix" what that output appears to show. If you
want to prove you touched nothing else, capture the staged paths outside your own
before and after and diff the two lists.

**Clean up after yourself: a right commit does not mean a safe index.** After you
commit, run the pre-commit checks *again* against the new `HEAD` and look at your
own paths in the **shared** index:

```bash
BASE=$(git rev-parse HEAD)
git diff-index --cached --stat "$BASE"
git diff-index --cached --diff-filter=D --name-only "$BASE"
```

A private index protects the commit you build. It cannot protect the shared one,
and it never touches it — so a snapshot of your files taken while your work was
half-written can sit there after your commit has moved past it, waiting for the
next person who types `git commit`. That is exactly how a finished feature ended
up staged for deletion minutes after it landed: 540 lines removed, the inverse of
the commit that added them, under a message about something else. This is a hazard
of the shared index existing at all, not of how you commit.

`git add` has its own hazard: `.git/index` is *one file* for every session, and
`git add <path>` adds to whatever another session left staged rather than staging
only your path. `git reset` first clears it — but that unstages everyone else's
work-in-progress, so prefer a private index, which never touches it.

**A check chained onto the command it guards is decoration.** The stat must be a
separate call with a human decision after it. Piped into the commit, the file
count scrolls past above output nobody reads until afterwards.

### Isolation and durability are different properties

Per-session worktrees (`./scripts/session-worktree.sh <module>`) give each session
its own working tree and its own index, and they genuinely remove a whole class of
failure: two sessions sharing one index, one carrying another's staging, a stale
blob overwriting a good one before it is committed. All of that goes.

**They do not remove the revert class.** Once merged, your content sits on `main`
like everyone else's, and a later commit built from a stale base reverts it there
exactly as before. Every revert on the day this was written hit content that was
**already committed** — not content anyone was holding in a working tree — so
worktrees would not have prevented a single one.

The dangerous reading is "the revert problem is solved", followed by the content
check being dropped at precisely the point it becomes the only thing left standing.
`git show <sha>:<path>` against the deploy pin stays mandatory.

This is the day's shape once more, and it caught the person announcing the fix in
the message announcing it: **a control that removes *some* failure modes gets
described as removing *the* failure, and the description is what people act on.**
The same shape as an exit code that "means pass", a private index that "was
immune", and a branch-protection rule sitting in settings enforcing nothing.

### A clean check is a photograph, not a guarantee

Every failure this section describes is one shape: **a reading whose scope was
wider than the thing measured.** An exit code read as a suite result. A working
tree read as `HEAD`. A file list read as content. A moving ref read as a fixed
fact. One index, read once, reported as the repository ongoing.

So say what you measured and when. "The index was clean at `<sha>` when I looked"
is true and useful; "the index is clean" is a claim about a shared file that
another session can invalidate in the time it takes to send the message. It was
invalidated within minutes, repeatedly, on the day this was written.

### Reachability, ref safety, and content are three different properties

All three passed on a commit whose fix was absent. Each answers a question the
others cannot:

| Check | Answers |
|---|---|
| `git merge-base --is-ancestor <sha> main` | is it still on the branch |
| `git update-ref … <old>` | did main move while I was building |
| `git show <sha>:<path>` | **is my change actually in the tree** |

**A commit surviving in `git log` is not evidence its content survived.** Verify
content against the SHA you care about — a deploy pin, not `HEAD`, since `HEAD`
moves. `git diff-tree --stat <sha>` is the cheap screen: a commit whose message is
about one module while rewriting three others is announcing itself.

Three traps found the hard way. `git show` piped into a linter reports phantom
parse errors on this machine — write the bytes to disk first. **A green test run is
evidence about the working tree at that instant, not about a commit**; the tree can
change between the run and the `git add`. And **before reporting a file missing,
confirm the path is spelled as it exists** — `git ls-tree -r --name-only HEAD -- <dir>`
rather than a filename from memory. Two near-miss alarms today were a checked path
that did not exist (`WebPluginController.php`, really `Web/PluginController.php`)
and a route looked for in `routes/api.php` that is enum-derived, so absent is
correct. Both times the reading was ABSENT and both times the tree was fine.

### Attribution is not available on this tree

Every commit carries the same `%an` — one machine, one git config — so authorship
cannot tell sessions apart, and session *names* are reassigned mid-conversation.
Do not infer who made a commit from its subject matter; that inference has been
wrong. The durable handle is the **commit SHA**. Name SHAs, not sessions.

## 5 · The four invariants that break things quietly

These come from the build plan. They are repeated here because breaking one usually
does not fail a test — it produces a system that is wrong in a way nobody notices for
a month.

### §3 — the hierarchy is fixed, and nothing moves between parents

```
Organization → Company → Sub Company → Franchise
```

The depth is fixed. A company and its first franchise are created **together, in one
transaction**, so "a company always has a place" is true by construction rather than
by a check somebody can forget.

**A parent is write-once.** `CompaniesController::update()` deliberately omits it
from the accepted fields. Every setting, assignment and roll-up below a company is
expressed in terms of where it sits, so moving one silently rewrites history: a
franchise's numbers would appear to have always belonged to its new parent. If you
find yourself adding a re-parent, you have misunderstood the request.

**The current view is the place you file.** `/me` sends every company and
franchise this person can *reach*. The top-bar switcher then names what they are
*looking at*. A Connect card, Add pane, company dropdown, or default `company_id`
that iterates `me.companies` (or `me.companies.first`) offers siblings of the
view — standing in A-1 Chimney, Everdoors is still in that list. Authority does
not flow up either: a company view cannot connect or edit the organization.
Use `companiesInView`, `franchisesInView`, and `filingCompanyId` on `Me`. The
switcher (`scope_picker_panel`) is the one control that lists reach. This leaked
in Inventory, Fleet and Phone and was fixed in each; they are now the worked
examples a new module copies, which is what AGENTS.md means by "copies
Inventory/Fleet/Phone". Do not ship a fourth leak. A company-view widget test
with a sibling in `/me` is the proof — `client/test/inventory_screen_test.dart`
("a company view does not offer sibling companies on New location") is the shape
to copy.

### A view-timezone window must be converted before it reaches a UTC column

`DashboardPeriod::$startsOn`, and anything from `Carbon::now($timezone)`, is a
**wall clock in the organisation's timezone**. A Carbon binds to a query as its own
wall-clock string with no conversion, so handing one straight to a comparison
against a UTC column puts the whole window out by the offset. Convert first:

```php
$period->startsOn->copy()->utc()
```

Seven glances in `app/Support/Dashboard/Glances/` do this, and `JobsGlance:107`
states the rule beside the call. It is worth knowing both directions this fails in,
because finding one will not find the other: a two-sided `whereBetween` binds late
and **drops** rows at the upper edge (Phone's `CallReport`, fixed in `1fb67ba` —
every evening call vanished from "today" and reappeared next morning), while a
one-sided `>=` binds early and **over-counts** (`HrGlance:93`, open as TODO #34).

Both are invisible in the morning and wrong in the evening, which is why neither
was ever reported by a user. A `DATE` column has no timezone to get wrong; only
datetimes are exposed.

### §6 — settings cascade upward

```
franchise → owning company → parent company → organization → registry default
```

Never read a setting directly from a row. Ask `SettingsResolver`. A setting is also
only offered at scopes that should control it (`allowedScopes`) — otherwise a
franchise administrator can weaken a policy the organization set.

### §4 — four gates, in this order

```
release flag → entitlement → permission → assignment
```

All four. A permission check alone is not access control here. **Every module is
gated by the tab permissions an organization grants to its own roles — nothing is on
for everybody.** A control that is offered must be a control that works: if the
answer would be 403, do not draw an enabled button.

When a policy refuses, it refuses **with a sentence**, and the client shows that
sentence. Two copies of a refusal reason drift; there is one, and it comes from the
server.

### §2.1 — six categories of configuration, and they are not interchangeable

Platform invariants · deployment config · release flags · entitlements · **tenant
settings** · **user preferences**.

The last two are the ones that get confused. A tenant setting is the
organization's and everybody sees it. A user preference is one person's and nobody
else does. Putting a shared fact in `users.preferences` means two colleagues cannot
agree about what they are looking at; putting a personal one in a tenant setting
means one person's choice moves everybody's screen.

## 6 · House rules

Not style preferences. Each of these was a correction.

**Nothing is hardcoded.** Everything a customer might need to change is configurable
*inside the app* — variables, workflows, automations, all of it. "Run this console
command" is never an acceptable answer to a customer need. If a new capability
requires a code change to configure, it is not finished.

**No pop-ups. Ever.** A new screen, or a right-side panel. Dropdowns and menus are
not pop-ups; a modal dialog is, and there are none.

**Every feature wires into automations.** Events, conditions, actions. A module that
emits nothing is half built. If a change genuinely emits nothing, say so explicitly
and give the reason — do not invent a trigger to satisfy the rule, and do not skip
the question.

**Design against what already exists.** Read the surrounding code first. There are
registries for most extension points — `SettingRegistry`, `ModuleRegistry`,
`WidgetRegistry`, `PermissionCatalogue`, `MailboxReaders` — and a new widget, module
or setting should be a class in one of them, not a client release.

**Build for every platform.** Web first, but desktop and mobile are coming. Nothing
may assume a wide viewport, a mouse, or hover. **It must work at 375px wide**, and
touch and pinch are first-class.

**Write for the person using it.** Plain words, honest states, no dead ends. Never
show a section number, a class name, or a word like "immutable" to a user. Say what
happened and what they can do about it.

**No AI-slop visuals.** No purple, no gradient stripes. The palette is pinned in
`client/lib/core/theme.dart` — take colours from there, never a literal.

**Show designs before building a tab.** For a new tab or major screen, produce
several alternatives as HTML mockups, rendered in the app's own chrome with the real
palette and real data, numbered so the owner can answer by number. Then build the one
they pick. Going straight to Flutter and getting it wrong is far more expensive.

**Number your questions.** When you need decisions, put them in a numbered list. The
owner answers by number.

## 7 · Comments: for decisions, not for narration

Decision records live in the code rather than in a folder (build plan §1: a decision
written beside the code it constrains gets read; one in a folder does not). That is
still true. What follows is the correction to how far it was taken.

**A long comment is for a decision that constrains the future.** §3's write-once
parent earns one — it is non-obvious, and undoing it silently rewrites history. So
does the MySQL key-order trap in section 8. So does "why this is not in
CompaniesController". The test: *would somebody reasonably do the obvious thing here
and be wrong?* If yes, write down why. If no, write nothing.

**Everything else gets an ordinary comment or none.** A method that clears a state
variable does not need a paragraph. `// set the value` is still worse than nothing —
the choice is between a real reason and silence, not between prose and prose.

**Say each thing once.** If a rule is written out in full in three files, two of them
will eventually be wrong. Explain it where it lives and point at it from elsewhere.
This is the same argument the code already makes about duplicated logic.

**If you change behaviour a comment describes, change the comment in the same edit.**
A paragraph describing a property the code no longer has is worse than no paragraph.

### Why this section was rewritten on 2026-08-17

It used to say "match this, it will feel excessive" and the result was measurable:
`client/lib/widgets/structure_canvas.dart` reached 2,933 lines — **1,513 of comment
against 1,150 of code** — and the feature it belongs to about 300KB across five
files. Every change after that pays to read it, so each one costs more than the last.

The prose was not buying correctness either. On the day that file peaked, two real
defects went through it untouched (an explanation strip crushing the canvas to
nothing, a stale sentence left on screen), and a defect that did *not* exist was
reported and confirmed with a confident paragraph explaining a mechanism the code
never performs. Length made a wrong thing look considered, which is worse than a
short comment, not better.

Depth where a decision is load-bearing. Silence where the code already says it.

## 8 · Testing

### The engine trap — read this before writing an assertion

**Production and the deploy gate run MySQL. A local sqlite run is not equivalent.**

MySQL does not preserve a JSON object's key order — it sorts keys by length, then
lexicographically — while sqlite keeps insertion order. So `{kind, id, x, y}` written
to a `json` column comes back as `{x, y, id, kind}`.

`assertSame` compares key order. Nine tests once passed locally and failed the real
gate for exactly this. **Never write an assertion that depends on the key order of
something read back out of the database.** Array *element* order is safe.

The same warning generalises: sqlite does not enforce `VARCHAR` length, has no
`REGEXP_REPLACE`, and does not understand `SHOW`. If a test touches any of those,
only the MySQL run tells the truth.

### Running them

```bash
cd client && flutter analyze && flutter test
```

The backend suite expects MySQL (`phpunit.xml` forces `DB_DATABASE=ezbizi_testing`).
On this development machine that schema exists as of 2026-08-18 — run
`php artisan test` with no sqlite overrides. sqlite still differs from MySQL
(JSON key order, `VARCHAR` length, `REGEXP_REPLACE`, `SHOW`); do not use it as a
gate. GD and Dompdf are still missing locally, so a handful of image/PDF tests
fail here and pass on the sandbox. See `docs/EZBIZI-DEV-ENVIRONMENT.md`.

### A test that cannot fail is not a test

After writing one, **delete the line of production code it targets and watch it go
red**, then restore. This takes seconds and it is the only thing separating a test
from a comment.

This is not theoretical caution. This codebase has shipped tests that passed against
the exact bug they claimed to catch: one measured the wrong widget, one accepted any
HTTP verb, one asserted on a value it had computed itself. Assume yours is one of
them until you have seen it fail.

Treat review findings the same way — including your own, and including a
confident one from another agent. On one change two independent reviewers
"confirmed" a defect that did not reproduce; the test written to prove it passed
against unmodified code.

### A guard is strongest exactly where it needs to be weakest

The other half of the rule above. A test that cannot fail is useless; a guard
that fires hardest on the case it exists to catch is worse, because it looks
like it is working.

Six of these turned up on 2026-08-28 alone, all in code behaving exactly as
designed, with the design pointed the wrong way:

- **The backup verifier could not go red.** `restore-check.sh` compared six
  named tables to catch "a dump interrupted partway through". Those six —
  organizations, companies, franchises, users, roles, permissions — are the
  FOUNDATION set, the first thing any dump writes, so a truncated dump leaves
  exactly them full. Six of the sixty-four non-empty tables, and it had chosen
  the six least capable of failing.
- **The landmine detector protected the landmine.** `index-landmines.sh` looks a
  staged blob up in history: recognised means a stale snapshot, safe to clear;
  unrecognised means somebody's live work, protect it. A staged DELETION has no
  blob, so an armed deletion of a 368-line file committed minutes earlier came
  back "live" and the clearing command was withheld — for the one entry on the
  list that most needed clearing, and the four beside it.
- **The report was wrong only in the evening.** A window built in the view
  timezone and bound against a UTC column dropped every call after 19:00 local,
  and those calls reappeared the next morning inside the following day's window.
  Correct again by the time anybody checked, which is why it survived in
  production and nobody ever reported it.
- **The gate tested a tree that no longer existed.** A hand-written list of
  directories to wipe before extracting the archive was missing `public`, so a
  file deleted by a commit survived in the sandbox and failed the very commit
  that deleted it. It fails honest work, and — the dangerous direction — it
  would equally have PASSED a deletion that live code still referenced.
- **The suite proved the first hop and said nothing about the feature.** Eight
  green tests on a recurring-task worker, not one of which completed a
  second-generation instance. "Service the truck every 3 months" serviced it
  twice and never again.
- **`/version.json` reports `1.0.0` build `1`.** It is pubspec's default, it has
  never changed, and it is the first file anybody reaches for to confirm what is
  deployed. It would report healthy for a build that was never shipped.

**The question that finds them:** *what does this look like when it is doing its
job, and is that distinguishable from it not being there at all?* If the answer
is no, the check is decoration. Prove it can say something other than "fine" —
doctor the input, watch it complain, then put the input back.

And when a check reports something implausible, suspect the check. The staged
deletion above was found because "matches no commit" is a strange thing to say
about a file sitting right there at HEAD — nothing had failed, the output just
read oddly.

### `git log -- <path>` will not show you the commit that deleted your work

The standing advice is to verify with `git show HEAD:<path>` rather than
`git log`, because a commit can sit in the log looking fine while its content is
gone. This is the next step: once you know content is missing, **`git log --
<path>` may not tell you who took it.**

Default history simplification hides commits that are not "interesting" for a
path. A stale whole-file write that removed your lines can be one of them:

```bash
git log a69e62d..main -- wordpress-plugin/tests/plugin-check.php               # 0 commits
git log --full-history a69e62d..main -- wordpress-plugin/tests/plugin-check.php # 5157df0
```

Same range, same path, and only the second finds the commit that took the lines
out. Measured on 2026-08-31, tracing 220 deletions across two modules.

**And before you conclude a whole file was rewritten, diff it with
`--strip-trailing-cr`.** On this tree two versions of a 250-line file appeared to
differ on every line and were identical apart from line endings. A session
nearly abandoned a correct restore on that evidence.

### Ask whether the answer is a BELIEVABLE SHAPE, not just whether you checked

"Verify before you claim" is about whether you looked. This is about whether what
came back could be true. It is the cheaper check and it fires earlier, because it
needs no second measurement — only a moment spent asking what a real answer would
look like.

Two on 2026-08-31, both caught this way and neither by a better method:

- A sweep reported TWELVE entries of `IMPLEMENTED_ACTIONS` as unreachable,
  including `task.create` and `time_clock.clock_in`. Twelve dead constants in
  shipped, working code is not a thing that quietly happens. The sweep had
  iterated `$m->actions`, which holds PERMISSION strings — view, create, edit —
  rather than `$m->automationActions`, which holds the ActionDefinition objects.
  A confident, precise, complete answer to the wrong question. The real number
  was two, and both were global action types offered by a different path.
- `scripts/index-landmines.sh` classified a file as "matches no commit —
  somebody is working on it" while that file sat at HEAD with 368 lines. Nothing
  had failed and no test was red; the sentence was merely strange. It was a
  staged DELETION, which has no blob to look up, so the rule protecting other
  people's work was protecting an armed revert of somebody's finished feature.

**The tell is usually a number or a claim that is too round, too large, or too
confident for the situation.** Twelve of anything wrong at once. Zero rows in a
table somebody is actively using. A file that both exists and does not. When the
shape is wrong, suspect the measurement before the system — the system has been
running longer than your query has.

This is not scepticism about results you dislike. A believable-shaped answer that
happens to be unwelcome still needs acting on; an implausible one needs checking
first, and usually turns out to be the instrument.

### A finding can be neutralised by being filed under one already forgiven

The believable-shape rule above asks whether the ANSWER is plausible. This is the
same failure one level up, where the answer is implausible but the CITATION makes
it look already-decided.

A live disclosure — an automation subject that broadcast one franchise's record to
every user in the organization — was filed as "mirrors a known, already-deferred
gap", pointing at a real note in `ModuleServiceProvider` about subjects-per-
trigger. Different interface, different methods; they never touch. And the note it
cited priced its own gap as harmless: *"what null costs is one affordance and
nothing else."* So a disclosure inherited a cosmetic verdict, and the person
reading the review saw a finding that had apparently already been considered.

**The mis-filing is invisible, because the note it points at genuinely exists and
genuinely was accepted.** Nothing in the citation is false. Only the match is.

So: when a finding is dismissed as covered by a known issue, open the known issue
and read what it actually says. "Similar in shape" and "the same problem" are
different claims, and the second one is doing all the work.

Related, from the same case: the reviewer classified it as a missing
*affordance* — franchise-scoped rules never firing — and did not notice it was
also a *disclosure*. One defect can sit in two categories, and being right about
the boring one is how the other gets closed.

### After a merge, verify the TREE — not your diff

`--filter` to the files you touched is the right discipline for your own work,
and it stops being right the instant a merge arrives. A merge is not a change to
your module; it is a change to the whole tree, and the moment it feels most
reasonable to carry on doing what you have done all day is exactly the moment it
is wrong.

On 2026-08-31 a session merged 118 commits of main into its branch, ran its own
three test files, got 96/96 and reported that as verified. The branch would have
gone red at the gate. The full suite — 1121/1121 — was two minutes away and
would have caught it in seconds instead of in a handover.

The full run also says something a scoped run structurally cannot: main was at
1117, the branch at 1121, so the four extra were the branch's own and nothing of
anybody else's went missing in the merge. A module-scoped pass cannot tell you
that no other module broke.

### Anything edited while staging is untested, however careful the run before it

`client/VERSION` and its `version_history.dart` note must agree, and a test says
so. Four separate sessions shipped the mismatch in three days. None of them was
careless and none had missed the rule — the file's own docblock states it.

The cause is ORDER. You run the gates, they pass, and THEN you bump VERSION
while putting the commit together. So the one file coupled to a test is the one
file the test never saw. Everything you ran was green and none of it covered the
change you made last.

**Bump the version and write its note BEFORE you run the gates, never while
staging.**

The general form matters more than the instance: a green run is evidence about
the tree as it stood when the run started. Every edit after that point is
unverified, and edits made during staging feel like packaging rather than
changes — which is exactly why they escape the instinct to re-run. If you touch
anything after the gates, the gates are stale.

### A coupled pair where only one half conflicts is sprung by resolving correctly

`client/VERSION` and the newest entry in `version_history.dart` must agree —
`version_history_test` asserts it. When two branches both bump VERSION, git
raises a conflict on VERSION and says NOTHING about the note, because the note
did not collide. Resolving the conflict correctly is what creates the mismatch.

That is the trap: the fix for the thing git told you about breaks the thing it
did not. Whenever you resolve a conflict, ask what else moves with the file you
just decided — the answer is not in the conflict markers.

### "Did nothing" and "did the wrong thing" need different detection

Most of the silent failures in this codebase are DEAD ENDS: a value saved and
never read, a screen that displays a setting nothing consults, a menu that could
be built and attached to nothing. The thing did not happen. Somebody eventually
notices, because they are waiting for an outcome that never comes.

A WRONG ANSWER is worse and rarer. `?label=SENT` on an Outlook mailbox returned
RECEIVED mail — 200, no error, no indication. Somebody checking what the business
had sent a customer would have been reading what the customer sent them, with
nothing to wonder about. Graph had the inbox hardcoded and IMAP ignored the
argument; only Gmail honoured it.

**They are found by different questions.** A dead end answers to *does this value
ever get read?* — static, greppable, findable by reading. A wrong answer needs
*does this path return what its name claims?*, which only a test that knows the
right answer can ask. That is why the label bug survived every review that read
the code and died the moment something asserted which URL got fetched.

### A green suite proves the code works, not that it is what you shipped

The tests measure the CODE. Until 2026-08-31 nothing measured the DELIVERY, and
they are not the same claim.

The deploy gate copied its sandbox with `git archive`, which runs on the Windows
machine, where `core.autocrlf=true` — and applies it. **1791 of 2131 files
differed from what production receives**, 430 KB of injected CR, on every deploy
the gate had ever run. Production was never affected: it is fed by `git push` and
checks out on the box, in LF.

2500 tests ran green against that tree for months, because PHP does not care
about line endings. The suite was not confirming the sandbox matched production;
it was demonstrating that almost nothing in it could tell. What finally noticed
was one anchored regex, by accident. Fixed in `b0a4c4e` with
`-c core.autocrlf=false` at the two archive call sites.

**The question to carry forward is not "are the tests green" but "what would be
different if the thing I am assuming were false, and does anything look there?"**

### Anchoring a regex with `$` makes the test depend on who checked the file out

`$` in multiline mode matches before a bare LF and NOT before a CRLF pair, and a
greedy token cannot consume the CR to reach it. So on a Windows checkout this
fails against a file that is byte-for-byte correct:

```
/^Stable tag:\s*(\S+)$/m   against  Stable tag: 1.0.2<CR><LF>   ->  0
                           against  Stable tag: 1.0.2<LF>       ->  1
```

**`^` is safe** — the stray CR sits at the END of the previous line, not the
start of the next. That one sentence classifies any regex in five seconds.

Use a negated class that excludes CR and LF, rather than `\S+$`. Three
independent sweeps agree the whole population was two occurrences, both in
`WebManagementTest`, both fixed in `7149803`, and zero in shipping code — which
matters, because a test that misreads a line ending goes red and somebody
investigates, whereas the WordPress plugin would quietly render the wrong thing
on a customer's page forever.

### A verification script must assert HOW MANY things it verified

The floor rule above applies to gates. It applies just as hard to the throwaway
script you write to convince yourself a refactor was safe — and there the stakes
are higher, because nobody reviews it and it runs once.

A session replacing 84 literals across 14 glances wrote a checker comparing each
new constant against the method it replaced. First run: "0 identical, 84
mismatched." That was the CHECKER being broken, not the refactor — Python's glob
returns Windows backslash paths, and `git show HEAD:app\Support\...` reads as
nothing, so every "old" value came back None.

**The dangerous version is the one that failed the other way.** Had it been
written to SKIP unreadable files instead of comparing them, it would have
compared zero pairs and printed a clean pass. A refactor across 84 values would
have been declared verified by a script that read nothing.

So: assert the counts, not just the result.

```python
assert files_read == 14
assert comparisons == 84
```

**A check that cannot distinguish "I compared them and they matched" from "I
compared nothing" is not a check.** One line converts a silent pass into a loud
failure.

Two bugs of this shape were made by the same session two hours apart, and both
were in the CHECKING code rather than the changed code, and both failed toward
"looks fine". That is the direction to expect: verification code is written in a
hurry by someone who already believes the answer.

### PHP's default 128M dies partway through a large filter

`php -d memory_limit=1G vendor/bin/phpunit --filter=...` for anything broad. The
default 128M runs a few hundred tests and then dies inside PHPUnit's result
cache, which reads as the suite breaking rather than as running out of room.

Combined with the schema rule, the full incantation is:

```bash
DB_DATABASE=ezbizi_testing_<yourmodule> php -d memory_limit=1G vendor/bin/phpunit
```

Also delete `.phpunit.result.cache` if a run dies oddly — it grows until it takes
the process down with it, and the deploy gate removes it before every run for
exactly that reason.

### A count is not a set: two changes in opposite directions look like one

The sharpest measurement failure of 2026-08-31 was the one where the NUMBER WAS
CORRECT.

A session merged main to pick up a fix, and their failing-test count went 17 to
16. The merge had fixed one red and introduced another — a table arriving without
its retention policy. Net movement: one, in the direction that looks like
progress. Had they reported "16 red, all known" without reading the list, they
would have handed the deploy desk a green-looking number concealing a fresh
failure, and it would have been believed, because the desk had asked for exactly
that number.

Every other bad measurement that day was a wrong number, and a wrong number can
be caught by re-measuring. This one cannot: re-running gives 16 again. **Only the
LIST shows it**, because the count is a lossy projection and the loss is
precisely the part that changed.

So when you report a suite's state after ANY change to the tree, report what is
in it, not how many. And when you receive a count that moved by one after a
change that could plausibly move it in both directions, ask for the list before
you believe the direction.

Found by the session it happened to, who read the list anyway.

### An upper bound is not a gate: floor anything whose scope is DERIVED

A ratchet asserting only `found <= baseline` passes when `found` is **0**. Break
the regex, point the scan at the wrong directory, rename the folder — comfortably
under the limit, green forever, and nothing says the measurement stopped
happening. Two of these shipped on the same morning: a colour-literal ratchet
scanning a directory, and a dashboard-icon gate diffing against a registry
filter. Both needed a second assertion, made separately from the rule:

```
expect(scanned, greaterThan(100))   // the scan actually ran
expect(found,   greaterThan(0))     // the pattern actually matches
```

Neither is the rule. They are the proof that the rule was measured.

**But do not floor everything.** A test looping a two-entry literal in its own
file has the identical structural hole and does not need it: emptying a literal
is a deliberate edit by somebody looking straight at it. A codebase full of
`assertNotEmpty` on hardcoded arrays is noise, and it teaches people to stop
reading the floors — which costs exactly what the rule was buying.

**The line is DERIVED versus LITERAL scope**, and the diagnostic is one question:

> *Can this scope become empty without anybody editing this file?*

A directory scan, a registry filter, a glob, a grep — yes, because something
upstream can move while the test sits untouched. A literal in the same file — no.
Floor the first; leave the second alone.

### Regenerating a golden: how to tell colour from movement before you do it

`--update-goldens` is the standard way to hide a layout regression, because it
makes any diff go away with equal confidence. The check that separates the two
takes about a minute and reads the ISOLATED and MASKED diff images the failing
run already wrote, BEFORE regenerating:

- **Text as solid blocks** means the glyph boxes did not move — every pixel of a
  glyph differs because its colour changed. Safe.
- **Paired ghosts** — the same element appearing twice, offset — is the signature
  of something MOVING. Not safe, and not a golden to update.
- **Borders as single outlines**, and rows, columns and panels still aligned
  across the whole frame.

That distinguishes "the colour changed" from "something moved" WITHOUT being able
to read any of the text, which matters because these frames render text as
featureless blocks in the first place.

Used on 2026-08-31 for eleven Tasks goldens after a brand-colour fix: every
changed region was an accent-coloured element in its original position, so
regenerating was correct. Say in the commit message what you checked for, so the
module's owner can review the reasoning rather than take the result on trust.

**A fix landing on main does not reach the worktrees, and "fixed in <sha>" reads
as though it does.** When this was fixed, twelve of the fourteen checkouts on this
box still held the broken assertion. Each one self-resolves on its next
`git merge main` — but not at the moment main goes green, so somebody runs the
suite, hits the identical red, and has just read a note saying it was fixed. If
you hit a red that a deploy note says is fixed, check whether YOUR checkout
contains the fix before you debug it:

```
git merge-base --is-ancestor <fix-sha> HEAD && echo "have it" || echo "behind"
```

**And the reason it was missed is worth more than the instance.** The sweep that
declared the population "two occurrences, full repo" used a search tool that
respects ignore rules — so it measured the tracked working tree and never
descended into the other checkouts. That is usually what you want, and it is
silently not what you want the moment worktrees exist.

That was the fourth instance in one day of a single shape: **a measurement whose
scope is narrower than the claim built on it.** A ratchet baseline measured before
a merge; golden images reviewed from the wrong tree; a file matching HEAD for a
reason nobody tested; a repo-wide sweep that saw one checkout. None were careless
— each used a reasonable tool and then described its output in broader terms than
the tool had earned.

**The trap while diagnosing it:** piping the file through `grep` before `od -c`
shows the line ending in a bare LF with no CR, because grep strips it. That is
how somebody talks themselves out of a correct diagnosis. Read it with
`file_get_contents` and the actual pattern.

## 9 · Deploying

### A comment claiming a guarantee the code does not provide

The most expensive stale comment is not the one that is merely out of date. It is
the one that ASSERTS A MECHANISM, because a reviewer reads the assertion instead
of checking the mechanism, and the comment becomes the evidence.

Measured 2026-08-31, in Tasks Phase 2: a `ConstrainedBox` with a `minHeight`
carried a comment saying it prevented silent row loss. It could not — its parent
was an `Expanded`, which passes TIGHT constraints, so the floor can never bite.
**Two separate reviews accepted it**, and three documents plus that comment all
asserted the mitigation worked. The code said otherwise and nobody did the
constraint math, because the comment had already answered the question.

The same session then shipped a fix wave that left the identical trap in another
file — a docblock repeating a claim they had just deleted from a status document
as untrue.

**A correction that reaches the document and not the code leaves the codebase
asserting something everybody has already agreed is false — and the comment
outlives the document.**

So: when a comment states that something is prevented, guaranteed or impossible,
that sentence is a CLAIM to verify, not context to absorb. The stronger the
guarantee it asserts, the more it is worth ten seconds against the actual
mechanism. A comment saying "this is why" is orientation. A comment saying "this
prevents X" is a test that was never written.

### The defect nobody will ever report: a healthy-looking row nobody checked

Everything else in this section is about a measurement that MISLEADS. This is the
other failure: a measurement taken correctly, then **discarded before it reached
anyone who could act on it**.

Two instances on 2026-08-31, an hour apart, both in Phone:

- A ring group of four where all four are on Do Not Disturb rings **nobody**. The
  pane said "4 people", because it counted MEMBERSHIP. The dialler already knew
  who was reachable and the screen was never told.
- A menu can be built, named, given options and attached to a line, and if it has
  no `menu` node the renderer looks for, **every call goes straight past it**. The
  pane listed it as healthy, because it counted EXISTENCE.

**Neither will ever be reported.** The caller does not know they missed a menu.
The owner does not know theirs is skipped. There is no complaint to investigate,
so it sits until somebody happens to build a screen that needs the fact.

In both cases the server ALREADY COMPUTED the truth and threw it away — one of
them (`describe()`) was running for every row with all but one boolean discarded,
so surfacing it cost nothing and no extra query.

**The tell is a status derived from existence rather than from function.**
"Attached", "configured", "4 members", "connected" — each answers a question
nobody asked. The question is whether it WORKS, and something upstream usually
knows. Ask what the renderer, the dialler or the dispatcher decided, and carry
that to the screen instead of re-deriving a weaker version of it there.

The second copy is its own hazard: deriving "who would actually ring" in the
client would have been a second implementation of the dialling rule, free to
drift from the first. The fix was one function both callers ask.

### A sub-second failure is infrastructure — but only if something answered

A suite that dies far faster than it could possibly run is an environmental
answer wearing a domain-shaped error message. The clearest case: a MySQL that is
still STARTING refuses with

```
SQLSTATE[HY000] [1698] Access denied for user 'root'@'localhost'
```

which reads as a credentials problem and will have you editing config. It is not
— the grant tables are simply not loaded yet. 698ms against ~30s for a real run
is the tell, not the message. Re-run before you change anything.

**THE TELL HAS A FAILURE MODE, and it is the rule's own shape turned on the
rule.** A session adopting it timed a liveness check at 77ms and read "still
starting" — but `mysql` was not on PATH in that shell and they had timed
`command not found`. The clock was honest; it was measuring a call that never
reached a server.

So the duration is only a valid signal **once you know the error came FROM the
database**. `1698 Access denied` proves a server answered. `command not found`,
a socket error, or a missing driver prove one did not. Both come back in
milliseconds and both look like evidence.

Confirm the error's ORIGIN first, then read the clock. And prefer a real
operation over a liveness probe either way: on 2026-08-31 a `/dev/tcp` port check
reported MySQL DOWN while an actual phpunit run passed against it in the same
minute — `/dev/tcp` is unreliable under Git Bash on Windows. Never believe a
negative probe.

### The gate is bound on MIGRATIONS, not on tests

Measured 2026-08-31: the test phase went from 1207s to 1474s — **22% longer for
about 5% more tests**. phpunit was using **1m52s of CPU in 19 minutes of wall
clock** — 2.7%, effectively idle — while MySQL was the real consumer, caught mid
`alter table franchises add unique ...`.

**The first version of this note said 60%, and that was wrong in the way this
whole section is about.** I compared the remote script's total elapsed time,
which includes an 18-minute `composer install`, against a previous run's TEST
duration alone. Two different spans, reported as one trend. Check what a number
covers before you put it in a document telling people to check what numbers
cover.

`RefreshDatabase` rebuilds the schema per test class. That day added roughly ten
tables across Scheduling, phone trust, phone extensions, staff messages and
Training, and every one of them made every rebuild more expensive. **The suite grew 5%
and the test phase grew 22%.**

So when the gate feels slow, do not go looking for a slow test. Check the CPU
split first:

```bash
ssh app 'ps -eo etime,time,cmd | grep phpunit'
```

Low CPU against high elapsed means it is waiting on the database, and the fix is
not in any test file. A long run with phpunit near 100% CPU is a different
problem and worth chasing.

**This compounds with every table anyone adds, and nothing surfaces it.** The
gate is the bottleneck on the whole fleet's release cadence; the thing making it
slower is schema, not code. The real fix is a migrated-once template rather than
per-class rebuilds, which changes how every test in the codebase sets up — not
something to attempt with five modules in flight.


```bash
./scripts/deploy.sh          # code + UI
./scripts/deploy.sh --code   # code only, skip the Flutter build
```

**Commit first.** The gate resolves `GATED_SHA` once with `git rev-parse main` and
then tests *that* commit — the exact tree about to ship, not your working directory,
and not whatever `main` becomes while the suite runs. The push is the same SHA. So no
commit freeze is needed during a deploy; anything you land mid-run simply ships next
time.

`client/VERSION` is bumped **once per release, by whoever cuts that release** — not
by every contributing commit. It is shown bottom-left in the app and on sign-in, so
a stale cache is visible rather than guessed at, and that only works if the number
means "what shipped". Many sessions committing into one tree would otherwise race a
single-line file, and four commits in one release batch cannot each own the number.

**Two release trains read this file, and both are legitimate.** A web deploy
(`scripts/deploy.sh`) is one. A store build is the other: `scripts/build-app.sh:78`
reads `client/VERSION` and line 88 derives `BUILD_NUMBER` from it, because Apple
requires a monotonic `CFBundleVersion` and Play a rising `versionCode` — so a store
build **must** bump it, independently of any deploy, or the upload is refused. A
bump you did not expect is more likely the other train than a violation. Ask before
reverting one.

Every step is a gate, in this order, and **nothing ships if any of them is red**:

1. The tree is synced to the sandbox on the box and the **backend suite runs there**
   — on MySQL, which is the run that counts.
2. `flutter analyze` and `flutter test`, locally.
3. The web client is built and stamped with the version.
4. **Code is pushed first, UI second** — deliberately. The UI goes straight into the
   live directory with no staging step, so shipping it first would put a new client
   in front of an old API.
5. The release backs up the database, migrates, syncs the permission catalogue,
   health-checks as the serving user, and only then swaps the symlink.

Read `docs/DEPLOY.md` before your first deploy. It documents several traps that have each
cost an afternoon — the `.env` fallback, the sudo requirement, the ownership rules,
and the certificate reload nobody was doing.

## 10 · Scheduled work

Some behaviour is not request-driven. If you are debugging something that "should
have happened", look here (`routes/console.php`):

| Command | When |
|---|---|
| `ezbizi:dispatch-automation-events` | every minute — the automations **outbox**. A write path inserts a row; this dispatches it. |
| `ezbizi:watch-mailboxes` | every minute — polls connected inboxes so `email.received` can fire |
| `ezbizi:expire-impersonations` | every 5 minutes |
| `ezbizi:expire-audit`, `ezbizi:expire-data` | nightly |
| `ezbizi:check-backups` | nightly, restore-verified |

The outbox pattern matters: **a write path never dispatches an automation itself**,
it inserts a row. So a failing rule cannot fail the request that triggered it.

## 12 · Working agreement

**Finish the whole task.** If part of it is blocked, do the rest and say plainly what
you left and why. Scaling the work down is the owner's decision, not yours.

**Solve it properly.** Read the framework source rather than working around it. A
structural fix beats a close-enough copy, and a second copy of a rule is how two
copies start disagreeing.

**Match the work to its size.** A few-file change is written directly and then
reviewed. Research phases, planning agents and large fan-outs are for work that
genuinely cannot be held in one head — a migration across many call sites, a new
module, a broad audit. Reviewing deeply is cheap; orchestrating deeply is not, and
wall-clock is paid per phase.

**Verify before you claim.** Check the box, run the command, read the output. Do not
report a gate green that you have not seen pass, and do not describe infrastructure
from a note that might be stale. If tests fail, say so and show the output.

**Say what you decided.** When a request is ambiguous, make the call a careful
colleague would make, state the assumption, and keep going. Ask only when two
readings would produce materially different work.

## 13 · Never

- Commit or log a credential, a token, or anything out of `CREDENTIALS.md`. **Moving a
  document into this repo counts as publishing it** — this repo is pushed to production,
  so scan anything you bring in. That exact mistake was made on 2026-08-17 and caught
  one commit before it shipped.
- Edit files on the production server as a way of shipping
- Point a test or a sandbox at the production database
- Add a re-parent, or any write that moves an entity between parents
- Move DNS to Route 53 — self-hosting is a settled decision (§15); the real gap is `ns2`
- Answer a customer need with a console command
- Add a modal
- Use a literal colour in the client
- Call a gate green without having seen it pass
